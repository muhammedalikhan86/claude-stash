# Shaw & Partners .NET estate guide

`%USERPROFILE%\source\repos` holds ~180 internal solutions:

- **`WebApis\`** (45) — backend APIs, one folder per system (e.g. `ComplianceWebAPI`, `PhoenixV3WebAPI`).
- **`Websites\`** (46) — frontends, mostly one-to-one with a WebApi (e.g. `Compliance`, `PhoenixV3`).
- **`ShawApplications\`** (78) — console jobs and Windows services (data syncs, report generators, interfaces to external systems).
- **`Database\`** — `CRMSSIS`/`ISSSIS`/`SOLSSIS`/`XrmSSIS` (SSIS ETL `.dtproj`/`.dtsx`), `DataWarehouse`/`ShawCentral` (`.sqlproj` SQL Server Database Projects), `PowerBI` (`.sqlproj` + `.pbix` reports). Only relevant to app work if a new project needs new DB objects.
- **`Libraries\ShawLibraries\`** — source for the shared `Shaw.*` class libraries, each with its own `README.md`. This is a **source repo you read, not one you reference directly** (see Golden rule below).

## Read the area index first

Each of the five areas has a **`README.md` at its root** that indexes every project in it: which
generation it belongs to, its target framework, and which `Shaw.*` packages it pins. **Read the
relevant area index before opening any project in that area** — it is the fastest way to find the
right existing project or the right template, and it carries per-area detail this file does not.

| Area | Index | What it settles |
|---|---|---|
| `WebApis\` | `WebApis\README.md` | Per-API generation and package pins; the three Gen-3 API templates; which APIs already integrate a given third party; where Crystal Reports is entrenched. |
| `Websites\` | `Websites\README.md` | Per-site frontend stack (Angular CLI / AngularJS / Web Forms); API pairing; why a website should almost never reference a `Shaw.*` library. |
| `ShawApplications\` | `ShawApplications\README.md` | Per-job generation, console vs Windows service, the canonical job shape, and the do-not-copy outliers. |
| `Database\` | `Database\README.md` | The `ShawCentral` config database in detail (including the write-back gotcha), and SSIS/`.sqlproj`/`.pbix` working conventions. |
| `Libraries\ShawLibraries\` | `Libraries\ShawLibraries\README.md` | Per-library version, dependency order, package-id vs folder-name traps, and the publish loop. |

These indexes are surveys of what exists, generated by scanning the actual project files, and they go
stale. Each ends with a "Regenerating this index" note describing how it was derived. Treat them as a
map to verify against the source, not as a source of truth.

Most of the estate is on EOL .NET Framework and is slated for a future .NET Core migration — but that migration hasn't started and is **out of scope for this skill**. This skill is only about building/extending software against the estate as it exists today, leaning toward the direction that migration will take.

## Golden rule: NuGet, never ProjectReference, for Shaw.* libraries

Every consuming project in the entire estate gets `Shaw.*` code via a NuGet package — **zero examples anywhere in `WebApis\` or `Websites\` use a `ProjectReference` into `Libraries\ShawLibraries`**, confirmed by repo-wide search. Never add one. If you need a change in a `Shaw.*` library, edit it under `Libraries\ShawLibraries\Shaw.<Name>\`, let its Release build auto-pack and auto-push (every `Shaw.*` csproj carries a `PushNuGet` MSBuild target that runs `nuget push` to the internal feed on Release build), then consume the new version as a package bump in the dependent project — never by pointing at the source folder.

Feed configuration already in place:
- Machine-wide `NuGet.Config` (`%APPDATA%\NuGet\NuGet.Config`) has a source named `Shaw` → `\\sic2tfs1\nuget\packages`. Most projects rely on this; only a handful carry their own project-level `NuGet.Config` (usually with a source named `Shaw nuget` → `http://sic2tfs1/Nuget/nuget`, the same feed's HTTP endpoint).
- Push endpoint used by the libraries themselves: `http://sic2tfs1/Nuget/nuget`, via `\\sic2tfs1\nuget\nuget.exe`.
- Note: `sic2tfs1` is *also* the legacy TFS server hostname (`SccTeamFoundationServer` bindings inside old `.sln` files) — that's an unrelated, older service on the same box. Don't confuse a TFS-binding hit with a NuGet-feed hit when grepping.

**v1.x vs v2.x are two different, incompatible package lines on the same feed** — different target frameworks and different internals (e.g. the config-loading mechanism). Match the line to your project's TFM:
- Classic .NET Framework project (net45/net472/net48) → pin `Shaw.*` **v1.x**.
- Modern SDK-style project (net8.0+/net10.0) → pin `Shaw.*` **v2.x** (the libraries are now built as `netstandard2.0`, versioned 2.0.x).
Full per-library detail: `references/shaw-libraries.md`.

## Which pattern to write new code in

The estate shows three generations of style. **Identify which generation a repo you're editing belongs to and match it** — see `references/generations-and-signatures.md` for the exact signatures (csproj shape, reference style, config style) and named examples of each. In short, oldest to newest:

1. **Gen 1 / 1.5** (oldest) — non-SDK csproj, .NET Framework 4.5–4.6.1, hand-copied DLLs via `HintPath` with no NuGet at all, or a locally-forked copy of common code (`ShawCommon`, `APESCommon`, `APESException`) instead of the shared `Shaw.*` libraries. **Do not imitate — see "Do not copy" below.**
2. **Gen 2** (current majority) — non-SDK csproj, .NET Framework 4.8, `packages.config` restoring `Shaw.*` v1.x, OWIN self-hosted ASP.NET Web API 2, `Web.config` + `Web.Debug.config`/`Web.Release.config` transforms. This is what most existing WebApis/Websites/ShawApplications look like today.
3. **Gen 3** (newest, in progress) — SDK-style csproj, `net10.0` (or `net8.0`), `PackageReference` to `Shaw.*` v2.x, minimal-hosting `Program.cs`, `appsettings.json`, layered `Domain`/`Application`/`Infrastructure` projects. Four live reference implementations exist in the codebase today — see `references/reference-projects.md`:
   - **API, multi-project**: `WebApis\PhoenixV3WebAPI\Phoenix.WebAPI\` (sits alongside the older Gen-2 `PhoenixV3WebAPI` project in the same solution — the rewrite-in-place pattern). The fullest example: Windows/Negotiate auth, AD role checks, CORS-with-credentials, Scalar/OpenAPI.
   - **API, single-project**: `WebApis\PersonalContactUpdatePIS\` and `WebApis\BpayLoaderInstructionsGeneratorWebAPI\` — clean-architecture folders (`Domain\`, `Application\`, `Infrastructure\`, `Controllers\`) inside **one** csproj, with a `.slnx` solution file. The lighter shape, and the better starting point for a single bounded service.
   - **Console/service job**: `ShawApplications\LowBrokerageReportV2\`.

**Decision rule:**
- **Brand-new standalone project** (a new WebAPI, a new console job, a new service) → follow **Gen 3**, copying the structure of whichever reference project above is the closer analog. This matches the direction the future .NET Core migration will take, so new work won't need rewriting later.
- **Change or feature inside an existing app** → match **that app's own existing generation**. Don't opportunistically modernize a Gen-2 app to Gen-3 mid-task unless the user explicitly asked for a rewrite/migration — that's a separate, larger initiative.

## Cross-cutting conventions (apply across all generations)

- **Config bootstrap order**: call `Shaw.Configuration.ConfigurationManager.GetConfiguration("<AssemblyTitle>", encrypt: false)` as the very first thing in `Main`/`Program`, before constructing any `Shaw.Mail` or `Shaw.DataAccess` object — they read config at construction time. Even Gen-3 apps still do this (check `Phoenix.WebAPI\Program.cs` for the current call site). **Gotcha**: this call pulls settings from a central `ShawCentral` SQL database keyed on the assembly title and can silently overwrite values already in `Web.config`/`appsettings.json`. Worse than in-memory overwriting: it **saves the DB values back into the app's config file on disk** (`OpenExeConfiguration` → `config.Save(...)`), and a `dbo.Configuration` row flagged `isGlobal` applies to *every* app in the estate regardless of assembly title. Its own connection to `ShawCentral` is hardcoded in `Shaw.ConfigurationManager\ConfigurationManager.cs` and cannot be redirected by config. If a setting seems to have the "wrong" value at runtime despite the config file looking correct, query `dbo.Configuration` for that assembly title *and* for `isGlobal` rows before assuming a code bug — see `Database\README.md` for the full mechanism.
  - **Connection strings are the one exception worth calling out**: `Shaw.DataAccess` v2.x resolves a connection string by checking `IConfiguration` first and only falling back to the `ShawCentral`-populated value if nothing's there (read `Shaw.DataAccess\DBConnectionBase.cs`'s `GetConnectionString()` for the exact current order). Practical direction: in a Gen-3 project, define connection strings under `ConnectionStrings:<DatabaseName>` in `appsettings.{Environment}.json` so they take priority and won't get silently swapped out — and use Windows-integrated auth on that connection string rather than a stored username/password. `Phoenix.WebAPI\appsettings.Production.json` is the current example of this done right; check it for the exact shape rather than assuming it hasn't changed. Most legacy `Web.config`s across the estate still carry plaintext SQL credentials — that's the pattern to move away from, not copy.
- **Logging / job-completion notification**: `Shaw.Diagnostics.Trace` (`Trace.Init(name)`, `Trace.TraceInformation`/`TraceException`, `Trace.Flush()`) plus `Shaw.Diagnostics.TraceMail`, which accumulates an HTML log and emails it at job end with the subject line prefixed `[SUCCESS]` or `[FAILURE]` depending on whether any errors were traced. This exact pattern repeats across most `ShawApplications` jobs — reuse it rather than inventing a new notification mechanism.
- **Errors**: throw/catch through the `Shaw.Exception` hierarchy (`CustomException` → `BusinessException` / `DataAccessException`, plus `UndefinedConfigurationException` for missing config) rather than raw `Exception`, so callers can distinguish business failures from infrastructure failures.
- **Windows Services**: register via `System.ServiceProcess.ServiceBase` + a `ProjectInstaller`/`ProjectInstaller.Designer.cs` pair, and ship a checked-in `Install.bat` that runs `InstallUtil /i <exe>`. No project in the estate uses TopShelf — don't introduce it as a new dependency without reason.
- **Windows Auth + role checks in a modern (Gen-3) API**: `Phoenix.WebAPI\Program.cs` is the reference for wiring up Windows Authentication in an ASP.NET Core project — it uses the `Negotiate` authentication scheme with a default policy that requires authentication on every endpoint unless told otherwise. For resolving *who* the signed-in user is and *which* AD groups/roles they hold, use `Shaw.ActiveDirectory`'s `NetworkCredentials` type rather than reading claims by hand — it needs a one-time `Initialize` call wired to the request's `IHttpContextAccessor` at startup, after which it exposes the current-user lookup and an AD-role-membership check (read `Shaw.ActiveDirectory\NetworkCredentials.cs` for the current method names/signatures — this is the mechanism to use for an Operations-vs-read-only style authorization split). If the API is ever called cross-origin from a separately-hosted Angular app, the CORS policy needs to explicitly allow credentials, or Windows Auth won't make it through the browser request at all — check `Phoenix.WebAPI\Program.cs`'s CORS setup for the current shape.
- **Before building a new third-party API integration, check whether one already exists** — grep `WebApis\` for the vendor's name first. For example, `WebApis\eSignatureWebAPI` already has a working Annature (e-signature) integration. Where an existing integration like this is outbound-API-only (no inbound webhook handling), treat that as a signal, not an oversight to just replicate: it means webhook/callback handling would be new ground for the estate, worth validating with the vendor and designing deliberately rather than assuming a pattern exists to copy. Also don't assume an existing integration's credential handling is the right example to follow — check it against the config-bootstrap guidance above rather than copying it as-is.

## Do not copy (found in the estate, but explicitly anti-patterns)

- Locally-forked common code (`ShawCommon`, `APESCommon`, `APESException`, `APESDTO`, `APESProvider`) duplicating what `Shaw.Common`/`Shaw.Exception` already provide — always take the shared package instead of re-implementing or forking it per-app.
- Hand-copied `DLL\` folders with a `PreBuildEvent` that shells out to an "Import New DLLS.bat"-style script (seen in `IntranetWebAPI`) — never manually vendor a DLL; always go through `packages.config`/`PackageReference`.
- VSS-style `_main`/`development` branch-folder layout inside a single repo (seen in `PhoenixDataSync`) — a pre-Git source-control artifact; use normal Git branches for new work, not folder-per-branch.
- `.NET Remoting`-based projects (e.g. `RemoteExec`, dating to Visual Studio 2008) — obsolete technology; use HTTP/a modern IPC mechanism instead if similar functionality is ever needed.
- Empty placeholder folders (e.g. `UBSTradeFile`) exist in the tree — not real reference implementations, ignore them.
