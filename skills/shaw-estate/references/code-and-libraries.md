# Code and libraries: where the estate lives and how to build in it

`%USERPROFILE%\source\repos` holds ~180 internal solutions:

- **`WebApis\`** (45) — backend APIs, one folder per system (e.g. `ComplianceWebAPI`, `PhoenixV3WebAPI`).
- **`Websites\`** (46) — frontends, mostly one-to-one with a WebApi (e.g. `Compliance`, `PhoenixV3`).
- **`ShawApplications\`** (78) — console jobs and Windows services (data syncs, report generators, interfaces to external systems).
- **`Database\`** — SQL and SSIS projects. Where database source lives (it is not only here): `databases-and-querying.md`.
- **`Libraries\ShawLibraries\`** — source for the shared `Shaw.*` class libraries, each with its own `README.md`. This is a **source repo you read, not one you reference directly**: consume them as NuGet packages (`nuget.md`).

Other Shaw repositories sit beside these, e.g. `shaw-plugin-dashboard` (Shaw Portal), which holds the
firm's IIS Deployment Standard and the precedent ADRs this skill cites.

## Before you build or answer

1. **Read the area index first.** Each of the five areas has a **`README.md` at its root** that indexes
   every project in it: generation, target framework, which `Shaw.*` packages it pins. Read it before
   opening a project in that area.
2. **Find where the estate already uses a library, database or service, and read that.** Working
   sample code carries constraints the library's own surface does not.
3. **Before saying some data, mapping or capability does not exist, search every project and schema
   in the estate.** If the search was not exhaustive, say what was searched instead of claiming absence.

Most of the estate is on EOL .NET Framework and is slated for a future .NET Core migration — but that
migration hasn't started. This file is about building/extending software against the estate as it
exists today, leaning toward the direction that migration will take.

## Which pattern to write new code in

The estate shows three generations of style. **Identify which generation a repo you're editing belongs to and match it** — see `generations-and-signatures.md` for the exact signatures (csproj shape, reference style, config style) and named examples of each. In short, oldest to newest:

1. **Gen 1 / 1.5** (oldest) — non-SDK csproj, .NET Framework 4.5–4.6.1, hand-copied DLLs via `HintPath` with no NuGet at all, or a locally-forked copy of common code (`ShawCommon`, `APESCommon`, `APESException`) instead of the shared `Shaw.*` libraries. **Do not imitate — see "Do not copy" below.**
2. **Gen 2** (current majority) — non-SDK csproj, .NET Framework 4.8, `packages.config` restoring `Shaw.*` v1.x, OWIN self-hosted ASP.NET Web API 2, `Web.config` + `Web.Debug.config`/`Web.Release.config` transforms. This is what most existing WebApis/Websites/ShawApplications look like today.
3. **Gen 3** (newest, in progress) — SDK-style csproj, `net10.0` (or `net8.0`), `PackageReference` to `Shaw.*` v2.x, minimal-hosting `Program.cs`, `appsettings.json`, layered `Domain`/`Application`/`Infrastructure` projects. Live reference implementations — see `reference-projects.md`:
   - **API, multi-project**: `WebApis\PhoenixV3WebAPI\Phoenix.WebAPI\` (sits alongside the older Gen-2 `PhoenixV3WebAPI` project in the same solution — the rewrite-in-place pattern). The fullest example: Windows/Negotiate auth, AD role checks, CORS-with-credentials, Scalar/OpenAPI.
   - **API, single-project**: `WebApis\PersonalContactUpdatePIS\` and `WebApis\BpayLoaderInstructionsGeneratorWebAPI\` — clean-architecture folders (`Domain\`, `Application\`, `Infrastructure\`, `Controllers\`) inside **one** csproj, with a `.slnx` solution file. The lighter shape, and the better starting point for a single bounded service.
   - **Console/service job**: `ShawApplications\LowBrokerageReportV2\`.
   - **Angular + .NET product on the intranet**: `shaw-plugin-dashboard` (Shaw Portal) — the precedent for hosting, app identity and app-owned data (`SKILL.md` § Standard architecture defaults).

**Decision rule:**
- **Brand-new standalone project** (a new WebAPI, a new console job, a new service) → follow **Gen 3**, copying the structure of whichever reference project above is the closer analog, and the Standard architecture defaults in `SKILL.md`.
- **Change or feature inside an existing app** → match **that app's own existing generation**. Don't opportunistically modernize a Gen-2 app to Gen-3 mid-task unless the user explicitly asked for a rewrite/migration — that's a separate, larger initiative.

## Cross-cutting conventions (apply across all generations)

- **Data access is `Shaw.DataAccess`, never EF Core** (Muhammed's standing rule, for estate consistency: every database-touching solution uses it). It is a thin raw-ADO.NET wrapper — no change tracking, no LINQ provider, no migrations — so any design leaning on an EF Core feature has to be re-argued early and hand-written. API surface: `shaw-libraries.md`.
- **Configuration:** `appsettings.{Environment}.json`. Never `Shaw.Configuration` /
  `SP_GETCONFIGURATION` (legacy, per the server administrator, 2026-10-12).
- **Mail settings (`Shaw.Mail`).** v2.0.0.1 has one constructor, `new Mail()`. It reads `MailServer`,
  `MailPort` and `ClientDomain` from classic `appSettings` (`System.Configuration.ConfigurationManager`),
  not from `appsettings.json`, and throws if one is missing (`Shaw.Mail\Mail.cs`). `Shaw.Configuration`
  used to fill those in. Without it there are three routes:
  1. **Copy them in memory at startup** from the `Mail` section of `appsettings.json` into
     `ConfigurationManager.AppSettings`, writing no file: the library stays unchanged. Precedent:
     `shaw-plugin-dashboard` portfolio-services, `Mail/ShawMailTransport.cs` (OFA-ADR-010, amended
     2026-11-03).
  2. **An `App.config`** (shipped as `<App>.dll.config`) holding the three `appSettings`.
  3. **A constructor that takes the values**: a planned, additive `Shaw.Mail` change, not yet on the feed.
     A library change comes only when no consumer-side route works, or Muhammed asks (`nuget.md`
     §Backward compatibility), so offer route 1 first.
  **When a project uses `Shaw.Mail`, ask the user which route to take**, and record the answer in the
  project's `CLAUDE.md` or an ADR.
- **Connection strings:** `Shaw.DataAccess` v2.x resolves a connection string by checking `IConfiguration` first and only falling back to the `ShawCentral`-populated value if nothing's there (read `Shaw.DataAccess\DBConnectionBase.cs`'s `GetConnectionString()` for the exact order). Define them under `ConnectionStrings:<DatabaseName>` in `appsettings.{Environment}.json`, with Windows Integrated Security. Most legacy `Web.config`s still carry plaintext SQL credentials — that's the pattern to move away from, not copy.
- **Logging / job-completion notification**: `Shaw.Diagnostics.Trace` (`Trace.Init(name)`, `Trace.TraceInformation`/`TraceException`, `Trace.Flush()`) plus `Shaw.Diagnostics.TraceMail`, which accumulates an HTML log and emails it at job end with the subject line prefixed `[SUCCESS]` or `[FAILURE]` depending on whether any errors were traced. This exact pattern repeats across most `ShawApplications` jobs — reuse it rather than inventing a new notification mechanism.
- **Errors**: throw/catch through the `Shaw.Exception` hierarchy (`CustomException` → `BusinessException` / `DataAccessException`, plus `UndefinedConfigurationException` for missing config) rather than raw `Exception`, so callers can distinguish business failures from infrastructure failures.
- **Windows Services**: register via `System.ServiceProcess.ServiceBase` + a `ProjectInstaller`/`ProjectInstaller.Designer.cs` pair, and ship a checked-in `Install.bat` that runs `InstallUtil /i <exe>`. No project in the estate uses TopShelf — don't introduce it as a new dependency without reason.
- **Windows sign-in and AD roles** in a Gen-3 API: `sign-in-and-ad.md`.
- **Before building a new third-party API integration, check whether one already exists** — grep `WebApis\` for the vendor's name first. For example, `WebApis\eSignatureWebAPI` already has a working Annature (e-signature) integration. Where an existing integration like this is outbound-API-only (no inbound webhook handling), treat that as a signal, not an oversight to just replicate: webhook/callback handling would be new ground for the estate, worth validating with the vendor and designing deliberately. Also don't assume an existing integration's credential handling is the right example to follow.

## Do not copy (found in the estate, but explicitly anti-patterns)

- Locally-forked common code (`ShawCommon`, `APESCommon`, `APESException`, `APESDTO`, `APESProvider`) duplicating what `Shaw.Common`/`Shaw.Exception` already provide — always take the shared package instead of re-implementing or forking it per-app.
- Hand-copied `DLL\` folders with a `PreBuildEvent` that shells out to an "Import New DLLS.bat"-style script (seen in `IntranetWebAPI`) — never manually vendor a DLL; always go through `packages.config`/`PackageReference`.
- VSS-style `_main`/`development` branch-folder layout inside a single repo (seen in `PhoenixDataSync`) — a pre-Git source-control artifact; use normal Git branches for new work, not folder-per-branch.
- `.NET Remoting`-based projects (e.g. `RemoteExec`, dating to Visual Studio 2008) — obsolete technology; use HTTP/a modern IPC mechanism instead if similar functionality is ever needed.
- Empty placeholder folders (e.g. `UBSTradeFile`) exist in the tree — not real reference implementations, ignore them.
