# Shaw.* library catalog

Source for all of these: `Libraries\ShawLibraries\Shaw.<Name>\`. Every one has its own `README.md` — read it before deep integration; this table is a fast-lookup index, not a replacement.

**Start at `Libraries\ShawLibraries\README.md`** — the area index in the repo itself. It carries the current per-library versions, the full dependency order, the publish loop, and the package-id-vs-folder-name traps, and it is regenerated from the csprojs. This file is the pattern-level summary; that one is the inventory.

All are built as SDK-style `netstandard2.0` class libraries versioned `2.0.x`, each with an identical `PushNuGet` MSBuild target that packs and pushes to the internal feed (`http://sic2tfs1/Nuget/nuget`) on every Release build — **with one exception, `Shaw.Google`** (non-SDK, net4.7.2, not in the solution, no push target; see its own README before depending on it). Older consuming projects still pin **v1.x** packages (net45/net472/net48-targeted, different internals) — see `nuget.md` for which line to use.

Two naming traps: the folder `Shaw.ConfigurationManager\` contains `Shaw.Configuration.csproj` and ships as package **`Shaw.Configuration`**; and `Shaw.Exception` ships as package id **`Shaw.Exceptions`** on the v1 line but **`Shaw.Exception`** on the v2 line, so it is not a straight version bump.

The `PushNuGet` command uses `-skipduplicate`, so **pushing without bumping `<Version>` silently does nothing** — that is the usual reason a consumer doesn't see a library change.

## Example v1.x pins seen in the wild (legacy consumers — do not use as version targets for new work)

These are illustrative only, to show the v1.x line exists and looks different from v2.x — always check the feed for the actual current version when pinning:

- `Shaw.ActiveDirectory` 1.5.1.3, `Shaw.Configuration` 1.3.2.1, `Shaw.DataAccess` 1.6.7.1 (`WebApis\StraightThroughPaymentsWebAPI\packages.config`)
- `Shaw.DataAccess` 1.6.5.0 (`ShawApplications\AETInterface\`)
- `Shaw.Common` 1.1.3 (`ShawApplications\IRESSInterfaceV2\packages\`)

There is **no estate-wide pinned baseline** — each project pins whatever was current when it was last touched, so the same package appears at many versions (`Shaw.DataAccess` spans `1.1.0` to `1.6.7.1`, `Shaw.Configuration` `1.0.0` to `1.3.2.1`). When adding a package to an existing Gen-2 project, match what its siblings in the same solution already use rather than jumping to the newest, unless you intend to test the upgrade. `ShawApplications\Fixed Income Daybook\` and `\NABInterface\` each pin *two different versions of the same packages* across their sub-projects — don't assume one version applies to a whole solution.

**The v1/v2 split is about internals, not a hard TFM incompatibility.** Since v2.x targets `netstandard2.0`, a `net48` project *can* consume it, and one does: `ShawApplications\ValidateACN\` is a net48 `packages.config` project pinning `Shaw.Common` **2.0.1** (`packages\Shaw.Common.2.0.1\lib\netstandard2.0\`) alongside v1.x for everything else. Match the line to the generation as the default rule, but don't be confused when you find a project that doesn't.

## Legacy raw-DLL drop (not a package source)

`Libraries\ReleaseBuilds\` contains only compiled `.dll` files (`Shaw.ActiveDirectory.dll`, `Shaw.Common.dll`, `Shaw.ConfigurationManager.dll`, `Shaw.DataAccess.dll`, `Shaw.Exceptions.dll`, `Shaw.Mail.dll`, `Shaw.Models.dll`) with no `.nupkg`, scripts, or nuspec — the output location for old-style (non-SDK) `Shaw.*` projects' `OutputPath`. It predates the NuGet pipeline and is unrelated to package consumption; don't reference DLLs from here in new work.
